# 실습 프로젝트 개선 기록

기존 Spring MVC 예제에서 보완한 기능과 변경 이유, 검증 결과를 기록합니다.

## 출발점

- 원본: 2023년 12월 27일 작성한 3개 커밋
- 기준 커밋: `7ca44a6`
- 구성: HTTP 메서드, 요청 바인딩, HTML·JSON 응답, Jackson 변환 예제
- 보완 대상: README, 실행 화면 안내, 입력 검증, 자동 검증 중심 테스트

기존 `com.sparta.springmvc` 패키지와 주요 실습 URL을 유지했습니다.

## 변경 내용과 판단

| 문제 | 개선 | 판단 근거 |
|---|---|---|
| 예제의 목적을 저장소 첫 화면에서 알기 어려움 | 프로젝트 소개, 실행 화면, 실습 가이드 추가 | 구현 범위와 검증 방법을 바로 확인하도록 구성 |
| 요청 바인딩 결과가 HTML 포함 문자열 | 바인딩 방식·이름·나이를 JSON으로 응답 | 데이터 전달과 화면 표현의 책임을 구분 |
| 문자열·객체 응답의 차이가 주석에 의존 | Content-Type 명시와 비교 화면 추가 | 실제 응답 헤더로 차이를 확인 |
| 잘못된 입력을 기본 오류에 맡김 | Jakarta Validation과 공통 오류 응답 | 누락·범위·타입 오류를 클라이언트에서 처리 가능 |
| 응답 문자열을 innerHTML에 삽입 | textContent 출력 | 입력이 HTML·이벤트 코드로 해석되지 않도록 처리 |
| 비원자적 공유 카운터 증가 | 인스턴스의 AtomicLong 사용 | 동시 요청 누락을 방지하되 영속화는 별도 범위로 유지 |
| API를 실행하려면 별도 도구가 필요 | Swagger UI와 웹 실습 도구 추가 | 명세와 실제 응답을 같은 서버에서 비교 |
| 폼 객체 요청이 OpenAPI에서 쿼리로 표현됨 | 폼 요청 본문 스키마를 명시 | 문서에서 실제 form-urlencoded 요청이 전송되도록 수정 |
| 결과 출력만 하던 테스트 | 값·상태·헤더·오류를 검증하는 테스트 | 회귀를 자동으로 발견하도록 개선 |
| 환경과 변경 후 검증 방법이 불명확 | Java·Gradle 정비, CI 추가 | 실행과 테스트 과정을 재현 가능하게 구성 |
| 분류되지 않은 예외가 Boot 기본 `/error` 본문으로 응답 (2026-11-09) | `ApiExceptionHandler.unexpected()`: ERROR 로그 + 500 `INTERNAL_ERROR`를 `ApiError` 형식으로 | 분류되지 않은 예외도 공통 오류 형식으로 반환하고 원인은 로그로 추적 |
| 바인딩 실패와 검증 실패의 응답 차이가 문서에만 존재 (2026-11-09) | `ErrorResponseContractTest` 4개 추가 | 같은 `age=abc`가 `@RequestParam`·`@ModelAttribute`에서 다른 `code`로 갈리는 규칙을 테스트로 고정 |

Java 17을 유지하고 Spring Boot를 3.1.0에서 3.5.16으로 정비했습니다. 기존 예제의 MVC·Jackson 2 구조를 이어갈 수 있도록 같은 메이저 버전 안에서 업데이트했습니다.

## 설계 트레이드오프

주요 설계 선택의 대안과 비용을 정리했습니다.

| 결정 | 선택하지 않은 쪽 | 이유 | 감수한 비용 |
|---|---|---|---|
| 요청 DTO와 응답 DTO를 `request.Star`·`response.Star`로 분리 | 하나의 `Star` 공유 | 요청의 검증 제약·스키마 설명과 응답의 JSON 직렬화 예제를 분리 | 유사한 필드 정의가 중복되며 같은 클래스 이름을 패키지 경로로 구분해야 함 |
| `ResponseEntityExceptionHandler`를 상속한 공통 핸들러에서 `ApiError`로 변환 | Boot 기본 `/error` 본문 또는 예외별 개별 핸들러 | Spring의 상태 코드 분류를 활용하면서 필드별 오류를 포함한 공통 형식 제공 | 상위 클래스의 예외 처리와 상태 코드 분류를 함께 확인해야 함. [요청 처리 흐름](STRUCTURE.md#3-요청-한-건이-응답이-되기까지) 참조 |
| Jackson 타입 변환과 알 수 없는 속성을 엄격히 처리 (`allow-coercion-of-scalars=false`, `accept-float-as-int=false`, `fail-on-unknown-properties=true`) | 숫자 문자열 등을 자동 변환하는 기본 동작 | 폼의 문자열 변환과 JSON 타입 검사의 차이를 비교. 실제 서비스에서는 클라이언트 호환성도 고려해야 함 | 숫자 문자열은 400으로 거부. 화면은 숫자로 변환 가능한 입력만 `Number()`로 바꾸고 `abc` 같은 값은 그대로 전송 |
| 방문 횟수를 인스턴스 메모리의 `AtomicLong`으로 관리 | DB·외부 캐시 저장 | 별도 저장소 없이 모델 값의 템플릿 전달과 공유 변수의 동시성 처리에 집중 | 재시작하면 초기화되며 서버 간에 공유되지 않음. 고유 방문자 수를 집계하는 지표로 사용할 수 없음 |

## 검증 근거

서버 테스트 40개와 실행 JAR 빌드를 통과했고, 2026-11-09에 오류 형식 테스트 4개를 더해 44개를 GitHub Actions에서 통과했습니다. 실제 서버와 브라우저를 연결해 요청·응답 흐름도 확인했습니다.

| 영역 | 확인한 동작 |
|---|---|
| 요청 | 바인딩 6종과 HTTP 메서드별 라우팅 |
| 검증 | 이름 길이·공백, 나이 0·150 경계, 누락·잘못된 타입·JSON 문법 |
| 응답 | 문자열·객체의 Content-Type, 공통 오류 코드 |
| 화면 | 정상·오류 입력, 안전한 텍스트 출력, 모바일·키보드 |
| 비동기 | 로딩, 중복 전송 방지, 연결 실패 후 재시도, 시간 초과 안내 |
| HTML | 정적·템플릿·동적 응답과 리다이렉트 |
| API 문서 | OpenAPI 요청 본문 형식, Swagger UI에서 JSON·폼 실제 전송 |
| 동시성 | 8개 스레드에서 컨트롤러를 총 200회 직접 호출해 증가값의 누락·중복 검사 |

웹 화면 캡처는 [images](images/)에서 확인할 수 있습니다. 자동화된 브라우저 검증은 `tools/ui/browser-smoke.mjs`에 보관했습니다. 화면 정적 검사는 색상 토큰 일치, 레이블, 상태 안내, 안전한 출력 방식을 확인합니다. 이 검사가 모든 접근성 기준 준수를 보증하지는 않습니다.

GitHub Actions에는 서버·브라우저 검증과 결과 아티팩트 업로드를 구성했습니다. 개별 실행 성공 여부는 저장소의 Actions 결과를 기준으로 확인합니다.

## 학습 범위

요청·응답 계약, 입력 검증, 오류 처리, API 명세와 실제 요청의 일치, 화면과 서버를 연결한 검증을 다룹니다. DB·인증·CRUD 및 실사용 환경의 성능 검증은 포함하지 않습니다.
